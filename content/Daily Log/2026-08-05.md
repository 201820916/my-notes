# Before DB

## DB가 나오기 전의 파일 시스템

- 응용 프로그램들이 각각의 독자적 파일을 갖고 있음
	- 프로그램 변경 시 파일 변경
	- 파일 변경 시 응용 프로그램도 변경
- 즉, 파일과 프로그램이 강하게 결합되어 있어 문제가 발생함.


- 유지보수성 문제 : 데이터의 물리 구조가 프로그램 곳곳에 하드코딩
- 데이터 종속성(데이터 디펜던시) 문제 : 데이터를 바꾸면 코드도 바꿔야 함
- 데이터 중복성 문제



## 파일 시스템의 문제

- 데이터 종속성
- 데이터 호환성과 표준화
- 데이터 중복성
- 데이터 무결성 침해
- 데이터 불일치
- 데이터 보안성 결여


# DB

- 파일 시스템의 한계 극복을 위한 테이블 형태의 관계형 데이터베이스
- 응용프로그램 <-> 데이터 사이에 데이터 베이스 매니징 시스템이라는 DBMS 배치
	- 서로의 변경 여파를 차단

## DB 구조 장점

- 사용자나 응용프로그램이 직접 DB에 접근 불가능 -> DBMS 통해서만 접근
- 데이터 독립성 보장
- 데이터 무결성 위반 차단
	- 위반 데이터 저장 차단
- 사용자 데이터 접근 제한 -> 높은 데이터 보안성

## DBMS : Data Base Managing System

- 데이터 본부 처리(경영) 시스템
- DB에 실질적 데이터를 조회, 추가, 제거, 삭제, 변경 수행


### DBMS 종류

|     | 오라클           | SQL Server   | MySQL               |
| --- | ------------- | ------------ | ------------------- |
|     | 하이엔드          | 상용(중대형)      | 오픈소스                |
|     | 금융, 대기업, 공공기관 | MS 생태계 기반 기업 | 스타트업, 웹사이트, 모바일 백엔드 |


 - 특히 오라클은 관계형 데이터베이스 상업화의 선구자
	 - IBM 먼저 기술 개발 -> 상용화 주저
	 - 오라클이 먼저 기업용 시장 진입 후 장악
		 - 금융권은 DB 유실/멈추면 큰 손실
		 - 오라클 DB는 글로벌 금융기업들의 크리티컬 환경에서 검증 거침
		 - 대규모 데이터 처리 속도, 복구 능력, 보안성 면에서 압도적 신뢰 습득

- 3제품 다 SQL 표준을 사용해 뿌리가 같은 관계형 데이터 데이터베이스


## DB의 종류

- Relation DB : 일반적으로 게임쪽에 적합 -> 정형화된 데이터 많음, 데이터 정확&무결 필요
- NoSQL(분산 DB) : SNS 적합 -> 비정형 데이터(영상, 음악 등), 방대한 양의 데이터를 관리


### RDB

- 엄격하게 정의된 DB 스키마를 요구하는 Table 기반 데이터 구조
- 대용량의 데이터가 계속 들어오면 스키마에 맞춰 변경해 넣기 위한 긴 시간의 다운타임 발생


### NoSQL

- 고정된 스키마 없음
- 빅데이터, 분산 환경에서 대용량 데이터 처리하기 위한 개발 
- 거대한 Map으로 Key-Value 지원


### 게임에선? RDB

- 데이터 무결성과 복잡한 쿼리 사용
- 트랜잭션(실패시 롤백)이 빈번함
	- 아이템 거래
	- 퀘스트 진행
	- 유저 로그인 / 아웃
- 일관성이 중요함



# SQL문

## DDL / 데이터 정의어

데이터를 직접 추가하고 조회하는 것이 아님
- 데이터를 담을 표나 데이터베이스 자체의 틀을 어떻게 구성할 것인지 정의
- Create : 데이터베이스, 테이블, 인덱스 등의 기본 구조 생성
- Alter : 이미 존재하는 테이블 구조 수정
- Drop : 테이블이나 DB 삭제
- Truncate : 데이터만 초기화


## DML / 데이터 조작어

- DB의 관리 핵심 조작어
- SELECT : 테이블에 저장된 데이터를 가져옴
	- 조회 : Read
- Insert : 테이블에 새로운 데이터 추가
- Update : 이미 존재하는 데이터 내용 변경
- Delete : 특정 데이터 삭제

## DCL / TCL

DCL : Data Control Language
- GRANT
- REVOKE

TCL : Transaction Control Language
- Commit
- Rollback
- Savepoint
- Release save point


# Key

## 기본 키 : Primary Key

- 테이블 당 1개만 존재할 수 있는 키
- 중복되지 않고 + 빈칸도 허용되지 않음 -> 그래서 기본키(ID)처럼 사용할 수 있는 이유
- NULL 포함 X

## 유니크 키 : Unique Key

- 특정 컬럼 값이 절대 중복되지 않도록 보장하는 장치
	- Ex : 회원가입 할때 이이디 중복 방지
- 테이블은 여러개의 유니크 키를 가질 수 있음
- NULL 가능 -> 예시) 전화번호

## 외래키 : Foreign Key

- 다른 테이블의 기본키를 참조하는데 사용


# 상용 게임의 DB 구조

### 실시간성이 없는 게임 장르

- 웹 기반 게임
- 방치형 게임
- 턴제 게임

- 실시간 서버가 있는 게임 속 실시간 액션이 필요 없는 기능
	- 웹서버 거쳐 DB 통신

## 실시간성이 있는 게임 장르

- MMORPG 같은 실시간 게임 장르는 하이브리드 방식입니다!
- 매우 중요하지만 자주 일어나는 일은 아닌, 단발성 작업들은 게임서버 - 웹서버 - DB서버를 통해 DB작업을 바로 수행
- 필드에서 얻는 잡템이나, 경험치 같은건 게임서버의 인메모리(Redis) 같은 것에 캐싱해두고 주기적(5분마다,10분마다)으로 배치 작업으로 DB에 저장.
- 물리적으로 서버가 종료되면 이 잠깐 사이에 저장 안된 데이터는 소실
	- Redis가 실시간으로 캐싱하고 있는 속도적 장점 때문에 덜 중요
	- 실시간으로 저장해야되는 데이터는 이렇게 임시 보관.
