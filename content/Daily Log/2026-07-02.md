# 시스템 구성 패턴(아키텍처 패턴)

- MVC, MVP, MVVM은 건축물이나 시스템의 구성을 의미하는 아키텍쳐 패턴이다.
- 디자인 패턴의 생성/행동/구조 패턴 -> 클래스와 객체를 어떻게 구성하고 관계를 형성할 것인가 같은 좁은 범위에서의 방법론
  - 아키텍쳐 패턴은 더 **거시적 관점, 넓은 범위에서의 시스템 전체를 어떻게 구성할 것인지** 고민하는 설계 방법
- 따라서, 각 패턴들이 각자 역할에 맞게 적용되고 아키텍처 패턴은 그다음 더 큰 범위에서 설계 및 적용하는맥락

## 왜 나왔는가?

- 프로그램이 거대해지면서 복잡도가 증가함
  - 어느순간부터 이게 유니티에서 출력을 위한 로직인지, 실제 중요한 데이터를 가공하는 로직인지 역할이 섞임
- 예시) HP라는 프로퍼티가 UI와 관련된 부분에서의 Slider용 변수인지, 아니면 실제로 플레이어의 HP를 의미하는 변수인지
- 예시) 플레이어의 레벨이라는 변수가 올랐는데, 다른 UI에서 일일이 이 레벨업을 알려주기 위해 해당 클래스를 알아야할때

- 협업 효율성이 점점 떨어짐
- 개발을 할때 다른 프로그래머와 같은 콘텐츠 작업시, A 프로그래머는 UI를 맡고, B 프로그래머는 데이터 관리를 맡았는데 계속
  1개의 코드를 수정해야하다보니 점점 충돌이 자주 발생

- 플랫폼이나 엔진으로부터 자유로운 구조가 필요해짐
- 엔진의 버전이나 특정 플랫폼으로부터 자유롭게 게임의 로직(논리)와 정보 처리
- 그리고 정보 전달에 대한 영역과 해당 논리의 결과값을 출력하는 요소를 분리하고 싶어하는 수요가 증가하게 됨
- 처리는 어떤 엔진에 종속된 로직이 아님! 
- 즉, 유니티 엔진을 언리얼 엔진으로 바꿔도 플레이어가 몬스터를 공격해서 피를 깎는다는 시스템은 그대로 사용가능 함

## MVC

- 시대적 상황 : 당시 마우스와 창 개념 도입되는 시기
- 하나의 데이터를 여러방식으로 보여줘야하는 요구 발생 -> 데이터 관리 / 그래픽 / 제어 분리가 MVC의 시초

![[사진/다운로드.png]]

### 동작 순서

- Action -> Controller
- 액션 처리 후 Controller -> Model 업데이트
- Controller -> View 선택
- View -> Model을 이용해 출력

### MVC 특징

- 1:N 구조 -> Controller는 여러개의 View를 선택 할 수 있음
- Controller는 View를 선택할 뿐 직접 업데이트 하지 않음(View는 컨트롤러를 모름)
- 장점 : 널리 사용되고 간단함
- View - Model 간 의존성 높음 -> 규모 커질수록 유지보수 어려움

## MVP

- WIN95 같은 GUI 운영체제 대중화
- MVC 뷰-모델 직접 결합은 유지보수가 힘듬
- 시대적 상황 : 웹 대중 화 전 거대한 데스크탑 앱 주류 -> 프레젠터라는 중간 관리자를 둬서 뷰와 모델을 격리하는게 세련된 기술
- 뷰와 로직을 완전히 분리하는 개념이 꽃을 피움 -> BUT 프레젠터가 직접 명령을 해주거나 기능이 많아진 뚱뚱한 프레젠터 문제 발생

### 동작 순서

- Action -> View
- View -> Presenter에 데이터 요청
- Presenter -> Model 데이터 요청
- Model -> Presenter 데이터 응답
- Presenter -> View 데이터 응답
- View -> 화면에 출력

### MVP 특징

- Presenter는 View와 Model의 인스턴스를 가지고 있어 둘을 연결하는 중간 관리자
- P와 V는 1:1 관계

### 장점

- V와 M 간 의존성 없음(P를 통한 데이터 전달)

### 단점

- V와 P의 의존성 높아짐

## MVVM

- WPF라는 프레임워크를 발표하면서 정립
- 시대적 상황 : 웹 기반의 데이터 서비스와 복잡한 UI가 쏟아지던 시절, UI를 그리는 방식과 데이터를 주고받는 방식이 너무 복잡해지며 이를 해결하기 위한 “데이터 바인딩”이라는 강력한 도구를 도입
- 의의 : 프레젠터가 하나하나 명령을 전달하던 MVP와 달리 뷰모델은 데이터를 “방송”만 하고 뷰가 이를 구독하게됨, 이 방식은 모바일 앱과 현대적 웹 프레임워크 표준이 되었고, 게임쪽에도 조금씩 이 구조에 대한 수요와 공급이 적용되게 됨

### 뷰 모델과 프레젠터의 차이

#### 공통점

- 관심사 분리 : UI와 데이터/로직을 분리하여 유지보수성을 높임
- 중재자 : M에서 가공된 데이터를 가져와 V에게 전달하고 V의 이벤트를 M에게 전달

#### 차이점

- V와의 관계
  - MVP: 직접적 명령(메서드 호출)
  - MVVM : 데이터 구독/바인딩
- View 지식
  - MVP : View의 인터페이스를 알아야 함
  - MVVM : V를 모름
- 업데이트 방식
  - MVP : 명령
  - MVVM : 선언형

## 관심사 분리

- 아키텍쳐 패턴에서 가장 중요한건 관심사 분리
- 내가 신경쓸게 지금 데이터(연산의 결과)를 위한 처리인가 아니면 출력(모니터, 스피커 등)을 위한 처리인가? 분리해서 접근

## 비즈니스 로직

- 게임의 규칙과 같은 단어
- 게임이 어떻게 돌아가는가? 에 대한 답변이 비즈니스 로직
- 테크니컬 로직은 이 비즈니스 로직을 구현하기 위한 기술적 방법의 논리이고, 비즈니스 로직은 기획적 논리

## 유니티의 사용자 정의 컴포넌트

- 아키텍쳐 패턴에 대한 개념이 없이 장기적으로 사용 -> 모노비헤이비어의 갓코드화
- 단일 책임 원칙 위반
- 데이터 구조가 바뀌면 -> 같은 코드 수정 / UI 바뀌어도 -> 같은 코드 수정 / 입력 방식 변하면 -> 같은 코드 수정
- 테스트 어려움
- 비즈니스 로직만 따로 떼서 단위 테스트(Unit Test)를 하기 어려움
- 재사용성 저하
- 로직만 재사용하고 싶어도 UI와 Input이 결합되어 코드 분리가 어려워짐

## 현대적 아키텍쳐 패턴의 근간 3요소

- 사용자 상호작용 용도인가?
- 데이터 OR 비즈니스 로직인가?
- 이 둘의 요청을 전달하고 연결하는가? -> 바인더 : 요청 전달, 모델변화 View에 연결

## 뷰(View = 보다)

- View = 어떤 것을 보거나 견해, 관점을 의미
- 사람이 인지 가능한 출력적 요소에서 사용되는 단어
- 사용자에게 보여지는 부분 (UI, 비주얼 요소 전부)
- UI에서 대표적으로 사용됨 -> 눈에 보이는 모든것이 뷰

### 뷰 개념의 역사

- MVC, MVP, MVVM을 배우기 전 뷰에 대해서 이해할 때 일반적으로 비게임계 관념에선 뷰를 UI와 동일시하는 경우 많음
- 게임에서 보여지는 것이 전부가 아니기에 뷰의 해석 범위가 더 넓어짐

## 모델(Model)

- **사용되는 데이터와 데이터가 직접적으로 변경되는 부분**
- 이전에 배운 PlayerModel 같은 [어떤 논리의 흐름과 연산에 사용되는 저장되거나 보관되는 인스턴스 데이터]도 이 모델에 해당함
- 서버가 있는 경우 클래스와 멤버변수 (프로퍼티 )를 꼭 두지 않아도 DB나 서버의 원본 데이터를 Model로 간주하는 경우도 있음
- 이런 경우 ViewModel에서 해당 내용을 바로 이어받아서 가공 & 관리
- 모델의 책임이 서버 패킷 데이터 클래스(DTO = Data Transfer Object)로 역할이 넘어가서 Unity 클라 코드에 Model을 따로 클래스로 두지 않도록 “타협”한 것 뿐, 모델이 없는 것은 아님!
- 왜 클라코드에 Model을 따로 만들지 않냐면 어차피 MMORPG 같은 정통적 서버-클라 구조에서는 클라가 관리해야되는 인스턴스 데이터가 많지 않고, 서버의 패킷 클래스가 Model 클래스와 어차피 역할이 동일하기 때문에 Model을 굳이 선언해서 코드와 파일수를 늘리지 않는 타협을 하는 것!
