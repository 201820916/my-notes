# 디자인 패턴 - 행동 패턴

## 옵저버 패턴

- 상태가 변함 -> 나를 구독하는 다른 객체에게 통지 -> 이 정보를 가지고 객체가 알아서 처리
	- 플레이어 HP 변화 -> HUD에서 UI 처리 알아서
	- 이벤트 구독과 해지 구조 필수적
- 이벤트 주도 아키텍처 설계
- 델리게이트 응용

1. Observer들이 Subject에 등록된다.  
2. Subject의 상태가 변경된다.  
3. Subject가 notify()를 호출한다.  
4. 등록된 Observer들의 update()가 실행된다.


## 상태 패턴(FSM)

- 객체 상태를 클래스화 -> 현재 상태에 따라 완전 변화
- 유한 상태 기계 구현 근간
- 플레이어나 몬스터 상태 변화 -> 조건문 ( IF - Else - Switch )로는 한계
	- IState라는 인터페이스를 하나 정의
		- 상태별 클래스 생성 및 제거

1. Context가 현재 상태를 가지고 있다.  
2. 클라이언트가 Context의 메서드를 호출한다.  
3. Context는 현재 State 객체에게 처리를 위임한다.  
4. State 객체는 상태에 맞는 동작을 수행한다.  
5. 필요하면 State 객체가 Context의 상태를 다른 상태로 변경한다.

단점
- 반드시 행동 전환을 위한 로직이 필요함
- 로직이 없다면 행동이 고정되어 있음

## 커맨드 패턴

- 실행할 명령을 하나의 독립 객체로 만들어 큐에 넣거나 되돌리기 지원
	- 턴제, 로그라이크, RTS 행동 구현 필수
		- 행동이 묶여있어 그 행동 순서대로 동작 가능
		- 심즈에서 심이 요리 -> 책읽기 행동 선택
			- 행동 리스트에 아이콘이 하나씩 추가되는 것


## 전략

- 실행할 **알고리즘이나 정책을 별도 객체로 분리**해서, 상황에 따라 갈아 끼울 수 있게 한 패턴
	- 캐릭터 자체는 “공격한다”는 행위만 알고, 실제 공격 방식은 전략 객체


## 중재자 패턴

-  객체끼리 직접 소통하지 않고 중재자 통해서만 대화
	- UI 매니저에서 인벤토리 오픈 시 상점도 같이 열어줘야 할때
		- UI의 직접 참조 X
		- UI 매니저를 통해 함께 열리고 닫힘
		- 게임 오브젝트 매니저의 InstanceId로 상호작용

## 오브젝트 풀링 패턴

- 객체를 필요할 때마다 새로 생성하고 삭제하지 않고, 미리 만들어 둔 객체를 재사용하는 기법
-  오브젝트 풀 패턴 -> 생성패턴 + 싱글턴 + 팩토리 결합 형태
- 잦은 Instantiate와 Destroy 방지

- 예시
	- 총알을 쏠 때 마다 Bullet 객체를 새로 만들고 삭제하 지 않음
		- 미리 Bullet 100개를 만들어 두고 필요할 때 꺼내 쓰고 끝나면 다시 풀에 반납
			- 생성 -> 사용 -> 삭제 (X)
			- 미리 생성 -> 꺼내서 사용 -> 비활성화 -> 다시 사용 (O)


## 비헤이비어 트리 

- 게임 AI의 행동을 **트리 구조로 표현하고 실행하는 방식**

BT 사용 이유
- 스파게티 코드화 : 상태 많아질수록 얽힘 정도가 늘어나 확장성 저해
- 재사용 X : 도망치기 상태는 고블린과 드래곤에게 재사용하기 어려움

- 따라서 상태 중심으로 생각하지 말고! Task(행동) 중심으로 계층구조를 짜자는 아이디어가 나옴
- 상태간의 복잡한 연결을 끊어버리고, 오직 “트리”의 부모 - 자식 관계로 AI의 우선순위와 흐름을 제어하게 만듬
- 상위 노드 -> 하위 노드로 구조를 탐색하며, 각 노드 실행 후 부모에게 “성공”, “실패”, “실행중” 중 하나를 반환
- 따라서 모두 성공하면 다음 행동 할지, 하나만 성공해도 다음 행동할지, 현재 행동이 실패하면 어떻게 할지,  행동을 해야되는 “말단”에서는 실제적으로 어떤 처리를 할지 같은 개념적 접근이 가능하게 됨
