
# QA(Quality Assurance)

- 게임 개발 프로세스에서 **출시전 최종 수문장** 역할을 하는 핵심 직군
- 게임 재미와 안정성을 사용자 입장에서 최종 점검하는 업무를 수행
- 특히 라이브 중 게임은 개발자가 일감을 완료해도 끝난 것이 아니며 QA팀의 최종 검수를 해야 Main(Dev) 브랜치에 적용될 수 있음
- 개발자 작업 -> 코드 컨펌(생략되는 경우 있음) -> 기획 검수 & QA 검수 병행 -> 최종 머지
- 개발자도 QA 검수와 대응으로 인해 머지가 너무 늦어지는 ㄴ경우를 방지하기 위해, Main 브랜치로 QA 브랜치를 따서 검수하기도 함
- 큰 규모의 회사는 일반적으로 QA의 최종 승인 없이 작업을 머지 할 수 없음


# 주요 업무

 - 기능 테스트 ( Funtional QA ) :  기획 의도 대로 게임이 작동하는지 검증
 - 호환성 테스트 ( Compatibility QA ) : 다양한 디바이스와 OS 환경에서 게임이 문제 없이 실행되는지 확인
 - 밸런스 및 테스트 성능 테스트 : 게임의 난이도 적절한지, 특정 구간에서 프레임 드랍이 없는지 플레이 환경을 최적화
 - 사용성 테스트 : 유저가 게임 플레이 시 불편한 것 없는지, UI가 직관적인지 테스트 -> 개선 사항 제시
 - 기획 내용과 구현물이 일치하는지 확인

  

## QA 업무 : 테스트 시트 작성 TC
 - TC 작성 : 무엇을 어떻게 테스트 할지 세부적인 체크리스트를 문서화
 - QA 포트폴리오에도 TC가 꼭 있어야 함
 - 팀 포트폴리오에서 QA를 지망하는 경우, 반드시 이 TC를 작성해보는 것을 추천 ( 추천 -  엑셀 )

  

  

### ID는 주로 가장 큰 콘텐츠 카테고리로 설정함

 - 인벤토리 : INV
 - 길드 : GUILD
 - 가챠 : GACHA
 
 - 테스트 항목은 테스트 할 상황을 대표하는 단어 사용
 
 - 중요도 : 이 스텝을 통과하지 않으면 절대 게임을 진행 할 수 없는 상황이나 유저 분쟁이 발생 할 수 있는 항목은 보통 매우 높음으로 설정
   - 중요하지 않거나 플레이에 지장을 주지 않는 다면 낮음으로 설정

 -  테스트 단계는 구체적 스텝을 명시, 해당 스텝이 중간에 여러 갈래로 나눠지면, 아래 행에 새로운 테스트 케이스를 행 추가해서 만듬

 - 예상 결과 기획적 요소와 기술적 요소가 모두 충족되는 완료된 상황 명시

 -  결과 표시가 가장 중요 -> Fail 항목은 일감으로 발행하거나 동일 일감의 하위 일감 또는 체크리스트로 작성

  

  

## QA 업무 : 버그 리포트

- 테스트 시트에서 항목 하나하나를 테스트하면서 발견된 이슈를 일감 관리 시스템(대표적으로 Jira)에 기록  
- 이때 단순히 진행이 안된다 보다는 정확한 재현 스탭을 기재

- 필요시 로그파일이나 스크린샷/영상/GIF 첨부해 개발자 즉시 수정 할 수 있도록 정교하게 정리

- QA는 게임 플레이 중 문제점을 찾아내고 독특한 스텝을 시도해보고 이를 일정한 스텝이나 규칙으로 정리할 수 있는 능력이 중요함 

- 100% 스텝을 찾는 것이 가장 중요, 50-80%정도의 스탭은 위급성을 따져서 개발자에게 공유

- 10% 미만의 간헐적 확률로 발생하는 버그가 가장 어려우며 이 경우 QA 팀장님에게 공유 또는 우선 버그 일감 발행해 개발팀에 추가적인 문제확인이 필요한 경우도 있음

  

## QA 업무 : 검증과 승인

- 검증 : 개발자가 수정 완료한 버그가 실제로 고쳐졌는지, 그 과정에서 다른 기능에 사이드 이펙트가 없는지 확인

- 출시 승인 : 게임에 배포 가능한 상태인지 최종 확인 및 보고서 작성

 - 일감 관리 시스템이 있는 경우 보고서보다는 덧글 또는 체크리스트를 일감에 기재하기도 함


## QA 필요 능력

- 분석적 사고 : 문제의 근본 원인을 추론, 발생 가능성이 있는 잠재적 위험 요소를 찾아내는 능력이 중요

- 커뮤니케이션 능력 : 개발자에게 버그 전달 시, 감정적 대립을 최소화 하고 정확한 정보를 전달

 -  기획자에게는 유저 관점의 피드백을 설득력 있게 제시

- 기술적 이해도 : 단순히 게임 플레이를 넘어 빌드 배포 과정, 엔진의 구조, 로그 확인법 등 기술적인 이해가 높을 수록 테크 QA로 더 깊이 있는 업무 가능 

  
## 게임 회사의 다양한 직군

- PM(Project Manager) : 개발자-비개발자 일정 조율, 프로젝트가 목표에 맞게 진행되도록 관리

 - 사업 PM, 개발 PM

- CM/GM : 커뮤니티 관리, 유저 문의 대응, 이벤트 기획

- 마케팅 : 게임 홍보, 타켓 유저 확보 -> 앱스토어 순위나 인지도 상승

- 사업 개발 : 플랫폼 협상, 퍼블리싱 계약

- 경영지원(HR)

- 재무/회계

- 법무팀

## 파견형 ( QA 전문 회사 )

- 전문 회사 소속, 다양한 게임 회사에 파견

- 팀바팀, 인맥쌓기 좋음, 반대의 경우도 있음

- 잠깐 있는 것에 익숙하고 주변 환경에 동요되지 않는 편이면 잘 맞음

- 개발팀 해체해도 회사 복귀하면 되므로 책임 관련으로는 분리

  

## 소속형( 게임 회사 직속 QA )

- 회사의 직속 QA로 채용된 경우

- 개발팀에서 같은 팀원으로 인식, 같이 일하기 좋음

- 버그 대응이나 책임 관련 부분에서는 조금 더 부담이 있는 편

- 개발팀 해체시 QA도 같이 정리 -> 안정성 부분에서 불리

- 라이브 출시시 대체 불가능, 해당 게임과 쭉 라이브 QA 커리어를 이어가는 경우 있음

  

## 개발자 입장에서 좋은 QA

- 커뮤니케이션 + 명확한 대화

 - 개발자에게 쩔쩔매거나, 버그를 봐주거나, 배려하는 QA는 오히려 나중에 누적된 버그나 팀에 더 큰 이슈를 발생시킬 수 있음

 - 개발자 입장에서 까다롭긴하나 표현을 잘하는 명확한 QA가 정말 도움이 많이 됨

### 비상 대응이나 요청이 가능한 QA

 - 게임 개발자 입장에서 어떤 형식이나 절차를 넘어, 긴급 대응을 해야하는 경우 QA 분들이 이런 비상상황에서 협업이 열려있으면 일하기가 정말 편함

 - 크런치 기간이나 출시 직전에 QA 분들이 같이 남아계시면 이만큼 든든한게 없음

### 깐깐하고 까다로운데 스텝을 기가막히게 잘찾는 QA

 - 아무리 깐깐해도 스텝을 기가막히게 잘찾는 인간 디버거의 능력을 장착한 QA 분들은 큰 도움이 됨

 - 개발자에게 이 100% 스텝만 알려줘도, 버그 해결 시간이 80% 정도 단축

 - 깐깐하고 까다롭다는건 그만큼 예외상황을 사전에 차단할 수 있다는 장점

  
### 절대! 게임 개발자로서 QA 분들을 무시하거나, 하대하거나, 협상하려하지 맙시다.

- 그분들은 해야할 업무가 QA이고, 게임 개발자에게 기획자보다 더 많은 권한으로 우리에게 피드백을 줘야하는 분들입니다.

- QA가 봐준 버그는 나중에 유저들의 제보로 더 큰 피해로 다가옵니다!

  
###  어쩌면 동료 프로그래머나 기획자보다 더 소중한 동료가 바로 QA입니다.

- 게임 개발자의 버그 대응 시간을 압도적으로 줄여주고 (스탭 체크)

- 게임 개발자가 정한 시나리오 외의 여러 시나리오에서 나오는 버그를 찾아주기도 하고, 그 시나리오들을 규격화(TC)해 다음에도 까먹지 않고 동일한 스텝들로 테스트를 반복할 수 있게 해주며 긴급할땐 게임 개발자를 여러 방면에서 지원해주는 든든한 동료입니다.

- 또한 게임 개발자 친구들이 QA 친구들 자리가 나면 소개해주기도 하고, 반대로 QA 친구들도 게임 개발 직군 자리가 비면 소개해주기도 합니다.

- 친한 경우 버그 제보 속도가 빨라지기도 하고, 게임 개발자가 시간이 너무 없을땐 버그를 좀 더 빨리 찾거나 다양한 스탭을 같이 시도해보는 등의 업무 분담도 진행합니다.

- 큰 규모의 게임에서 출시를 했던 팀은 QA가 있었고, 게임 개발자가 고생만하다가 출시도 못한 팀은 QA 직군이 부재했던 개인적인 경험을 되돌아볼 때, 아무리 프로토 타입의 게임이어도 QA의 존재 유무는 중요하다고 생각합니다.
