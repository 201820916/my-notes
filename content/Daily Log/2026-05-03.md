- 종속성 지옥

- 메모리 관리
	- 에셋 번들 : Unload(true)와 Unload(false)의 차이를 완벽히 이해해야함
		- 참조카운팅을 직접 구현하지 않으면 메모리 누수와 크래시가 빈번히 발생
	- 어드레서블 : 레퍼런스 카운팅 내장, 호출 1번으로 메모리 안전한 해제

- 경로 및 이름 관리
	- 에셋 번들 : 경로와 이름을 코드로 정확히 입력해야 로드 할 수 있음
	- 어드레서블 : 설정한 주소 문자열 하나로 로드

- 빌드 및 테스트
	- 에셋 번들 : 수정사항 확인을 위한 매번 번들 빌드
	- 어드레서블 : 패스트 모드 등을 통한 에셋 로딩 즉시 테스트

	- 유니티는 싱글 스레드 기반, 대부분의 로직을 밴드시 메인 스레드에서만 수행
	- 워커 스레드
		- 메인 스레드 외 백그라운드에서 복잡한 계산을 대신 해주는 보조 스레드
		- Unity의 C# Job System을 사용해 안전하고 효율적 활용 가능
	- 다만, 먼저 싱글 스레드 비동기를 잘 이용하도록 연습하는것을 추천

- 비동기
	- 결과가 나올때까지 기다리지 않고 다음 일을 하겠다
	- 스레드는 이 방식을 구현할 수단
	
	- 멀티 스레드 기반 비동기
		- 어떤 작업을 별도의 워커 스레드에 던지고 메인 스레드는 계속 게임 작업 수행
			- 어드레서드 파일 로딩
			
	- 싱글 스레드 기반
		- 코루틴
			- 스레드 새로 생성X, 메인 스레드 안에서 이번 프레임에 할만큼만 하고
			- 다음 프레임으로 작업을 미룸
			- 동시에 일하는 것은 아님 BUT 사용자 입장에선 멈춤이 적어 비동기 처럼 보임


- 장점
	- 자원활용 극대화
	- 사용자 경험 향상
	- 높은 처리량

- 단점
	- 설계 및 구현 복잡성
	- 디버깅 어려움
	- 데이터 일관성



## IEnumerator

- 컬렉션(리스트, 배열 etc..) 요소를 순회하기 위한 인터페이스
	- in 코루틴 - 코드의 실행 중간 지점을 기억하고 나중에 다시 시작할 수 있는 기능 위한 활용
	- Current : 현재 가리키는 데이터
	- MoveNext() : 다음 지점으로 화살표를 옮기고 데이터가 있다면 True, 없다면 False 반환

### 코루틴 

- 실행을 잠시 중단했다가 원하는 시점에 다시 중단 지점부터 작업을 재개하는 특별 함수
	- yield retrun 키워드 : 함수의 이 지점부터 다른 작업을 할 수 있게 양보
		- 정해진 조건이 되면 이 지점부터 다시 실행

#### 코루틴 활용

- 시간 기반 로직 제어
	- Update()에서 타이머 변수를 만들고 deltatime을 더하며 체크하는 작업
		- 이를 코드 한줄( yield return new WaitForSeconds)로 해결

- 절차적 연출
	- 애니메이션 재생 -> 1초 대기 -> 사운드 재생 ->이펙트 생성 같은 순차적 연출 작성
		- Update 보다 가독성 좋음

- 분산 처리
	- 수천 개의 오브젝트를 한 프레임에 생성 시 렉 유발
	- IEnumerator 내 루프를 돌며 중간중간 yield return null -> 작업 나눠서 처리 가능

- 주의점
	- GC : 반복문 안에서 계속 호출시 매번 새로운 객체의 생성으로 인한 메모리 부하
		- 자주 쓰는 시간값은 미리 멤버변수로 캐싱 추천
		
	- 생명주기 : 코루틴을 실행한 GameObject가 Disalbe 되거나 Destroy 되면 코루틴도 함께 멈춤

	- 반환형 : 반드시 IEnumerator를 반환형으로 가져야 유니티 코루틴 시스템이 이를 인식하고 관리

#### 코루틴 원리

- StartCoroutine : 유니티 엔진에 IEnumerator를 매 프레임 체크해달라고 등록
- yield return : 현재 함수의 실행 상태를 박제하고 제어권을 유니티 엔진에 돌려줌
- Condition Check : 유니티 내부적으로 MoveNext()를 실행 -> yield 조건 만족 확인
- Resume : 조건이 맞으면 멈춘 지점 바로 다음부터 코드 재개

## 유니테스크

- async / await는 Unitask가 나오기 이전에 도입된 비동기 프로그래밍 문법
- 이 문법을 이용한 유니티 게임 엔진 환경 최적화해서 사용할 수 있게 한 오픈 소스 라이브러리
- 특징 : 복잡한 콜백 지옥이나 쓰레드 관리를 "동기적인 흐름처럼" 읽기 쉽게 만들기 위해 등장

유니태스크
- async / await 같은 C#이 기존에 가지고 있는 문법적 요소를 갖고 있음
- UniTask : 유니티 성능(GC 등)을 극복하기 위해 만든 유니티 전용 “비동기 객체”
- 요약 : 유니티를 위해 맞게 튜닝한 Task


#### 표 정리

| 구분      | 표준 C# Task                            | UniTask                              |
| ------- | ------------------------------------- | ------------------------------------ |
| 메모리 할당  | 실행될 때 마다 힙 메모리 사용<br>GC 유발            | ValueTask 기반으로 설계되어<br>가비지 생성이 거의 없음 |
| 유니티 최적화 | 유니티 엔진루프를 모름<br>(Update, FixedUpdate) | 유니티의 특정 시점(Yield)이나<br>라이프사이클에 최적화   |
| 추가 기능   | 일반적 비동기 작업 위주                         | WaitUntill, Delay 등<br>유니티 맞춤형 기능 제공 |


| 특징    | 코루틴                            | Unitask                      |
| ----- | ------------------------------ | ---------------------------- |
| 반환값   | 불가능                            | 가능                           |
| 메모리   | 객체 생성 및 가비지 발생                 | 구조체 기반이라 가비지가 거의 없음          |
| 예외 처리 | try-catch 사용 불가                | 표준 try-catch 완벽              |
| 성능    | 유니티 엔진이 매 프레임 리스트를 <br>순회하며 관리 | C# 비동기 기능을 활용해 <br>훨씬 가볍게 동작 |
| 종속성   | MonoBehaivor가 있어야 실행가능         | 일반 클래스나 UI로직 등 어디서든 실행 가능    |
| 타입    | Class                          | Struct                       |
| 메모리   | 힙                              | 스택                           |
| GC 부담 | 호출마다 누적                        | 거의 없음                        |
| 박싱 발생 | yield return시 발생 가능            | 발생 X                         |

- 코루틴 단점
	- 함수 종료시 값 리턴 불가능
	- StartCoroutine()로 이름을 전달해 호출
	- 직관적이지 않음
	- 코루틴 호출마다 IEnumerator 객체 생성(힙메모리) -> GC 유발 가능
		- Unitask는 이를 획기적으로 줄일 수 있음


#### MEMO

어쩔 수 없이 코루틴을 사용해야 하는 상황이라면 -> UniTask를 고려해볼만 하다
- 어떤 행동 후에 Update가 아니라 한번만 시간대기하면 되는 경우 (물체 상호작용이나
스킬의 쿨타임)
- UI가 일정 시간 후 자동으로 닫혀야하는 경우
- 1프레임 대기 후에 처리가 필요한 경우 (UI나 물리 관련으로 1프레임 뒤에 올바르게 변경된
값을 기준으로 추가적인 처리를 해야하는 경우)

단, 코루틴이나 비동기처리가 굳이 필요 없는 상황이라면, 코루틴이든 UniTask든 굳이 설계와
코드의 복잡도를 올릴 필요가 없다 (비동기가 무조건 좋은게 아니다!)
- 추적이 어려움
- 데드락 : 비동기 작업끼리 서로 완료되길 무한히 기다리는 상태
- 상태 오염 : 비동기 함수가 데이터 수정 중 다른 함수가 동일한 데이터 수정 시
- 순서 보장이 어려움 : 흐름이 꼬이면 Null 에러가 발생하기 쉬움
- 비동기는 공짜가 아님 : 대기 중인 비동기 작업은 메모리에 올라가고, 작업상태의 임시
저장과 복원 과정에서 CPU자원이 소모됨


## 인스턴스(다이나믹) 데이터


| 구분  | 인스턴스 데이터  | 세이브 데이터        |
| --- | --------- | -------------- |
| 위치  | RAM 메모리   | DISK (HDD/SSD) |
| 속도  | 매우 빠름     | 상대적 느림         |
| 지속성 | 게임 종료시 삭제 | 유지됨            |
| 형태  | 변수, 객체 참조 | JSON, 바이너리 파일  |



- 특정 인스턴스가 현재 가지고 있는 실시간 상태값
	- 현재 체력, 현재 좌표, 장착중인 아이템 ID 등...
	- 휘발성 : 인스턴스 데이터는 게임을 종료하거나 씬 전환시 적절한 처리가 없으면 메모리 에서 사라짐
	- 따라서 플레이어는 적정 시점에 플레이 데이터를 저장해야함

- 저장 방식
	- 데이터 직렬화
		- 인스턴스 클래스에 담긴 복잡한 데이터를 저장 가능한 형태로 변환
			- JSON, XML, Binary
		- 파일 저장 : 변환된 데이터를 Application.persistentDataPath 경로에 파일로 저장
		- 로드 : 게임을 다시 켤 때 파일을 읽어와서 다시 게임 내 인스턴스 클래스의 변수들에 값을 대입


## 직렬화 / 역직렬화

직렬화(Serialization)와 역직렬화(Deserialization)
- 데이터를 '전송'하거나 '저장'하기 위해 데이터의 형태를 변환하는 핵심 과정

직렬화 (Serialization)
- 직렬화 는 메모리 속에 복잡하게 얽혀 있는 객체(인스턴스)를 파일로 저장하거나 
	네트워크로 보낼 수 있도록 한 줄로 나열된 데이터 형식(바이트 스트림 , 문자열 등)으로 바꿈
	
-  비유: 레고 성(객체)을 다른 집으로 보내기 위해 조각조각 분해해서 박스에 차곡차곡 담는 과정과 같음

- 유니티에서의 용도:
	- 현재 게임 상태를 JSON이나 Binary 파일로 저장할 때.
	- 에디터의 인스펙터(Inspector) 창에 변수 값을 노출시켜서 수정할 때 (\[SerializeField]).
	- 멀티플레이 게임에서 내 위치 정보를 서버로 보낼 때.





역직렬화 (Deserialization)
- 역직렬화 는 직렬화의 반대 과정
- 저장된 파일이나 수신된 데이터를 다시 읽어와서 메모리 상의 활성화된 객체(인스턴스 )로 복원

-  비유: 박스에 담겨 온 레고 조각들을 설명서(클래스 설계도)를 보고 다시 성(객체)으로 조립하는 과정입니다
- .
- 유니티에서의 용도:
	-  세이브 파일을 불러와서 캐릭터의 스탯을 복구할 때.
	-  서버에서 받은 데이터를 바탕으로 적 유닛을 화면에 생성할 때.



| 방식              | 특징              | 장점                       | 단점                        |
| --------------- | --------------- | ------------------------ | ------------------------- |
| JsonUtility     | 데이터 -> JSON 문자열 | 가독성 좋음<br>웹 통신 유리        | 복잡한 데이터 구조<br>처리가 어려움     |
| BinaryFormatter | 데이터 -> 이진법      | 용량 작음<br>속도 빠름<br>보안성 유리 | 사람이 읽을 수 없음<br>호환성 관리 어려움 |
| XmlSerializer   | 데이터 XML형식 변환    | 구조가 명확하고 규격화             | JSON보다 데이터 용량 큼           |
