### 디자인 패턴 - 생성

#### 생성 패턴 - 싱글턴

싱글톤은 왜 나왔는가?

- 핵심 로직을 관리하는 매니저
  - static이 아님
  - 중구난방한 곳에서 new가 되어 접근 불편함과 검색 피로도 상승
  - 예시) 1번씬의 매니저 정보와 2번씬의 매니저 정보가 불일치

  - 개선
  - 이 프로그램에서 "나는 단 1개이며 어디서든 접근 가능"을 보장

#### 생성 패턴 - 팩토리(적용 전)

```
public class Goblin
{

}

public class Slime
{

}

public class Orc
{

}

Goblin goblin = new Goblin();
Slime slime = new Slime();
Orc orc = new Orc();
```

IF - Goblin 생성 방식이 바뀌면? → Goblin()이 들어간 모든 코드 수정

- 유지보수 저하

#### 생성 패턴 - 팩토리(적용 후)

```
public abstract class Monster
{
  public string Name;
  public int Hp;
  public int Attack;
} // 내용물이라고 생각

public class Goblin : Monster
{

}

public class Slime : Monster
{

}

public class Orc : Monster
{
}

// 포장지라고 생각

MonsterFactory factory = new MonsterFactory();

```

Monster()에게 Goblin() 하나 만들어 달라고 요청 → 생성

#### 생성 패턴 - 제네릭 팩토리

```
public abstract class Monster
{
  public string Name;
  public int Hp;
  public int Attack;
}

public class Goblin : Monster
{
  public Goblin()
  {
  Name = "고블린";
  Hp = 100;
  Attack = 10;
  }
}

public class Slime : Monster
{
  public Slime()
  {
  Name = "슬라임"; Hp = 50; Attack = 5;
  }
}

public class Orc : Monster

{
  public Orc()
  {
  Name = "오크"; Hp = 200; Attack = 20;
  }
}
```

\<T> 를 이용해 타입을 매개변수처럼 받아 객체를 생성하는 팩토리

### where T : Monster, new()

- T는 몬스터를 상속해야 하고
- 매개 변수가 없는 생성자가 있어야 한다.
- 즉, Monster 상속받은 생성자만 활용 할 수 있음
-

- 핵심 : **객체를 만드는 주체**가 객체가 뭔지 몰라도 만들 수 있도록 한다.
  - 상속을 통해 만들 대상들의 추상적인 대표 클래스 정도만 알고 있음
  - 어떤 객체인지는 만들때 정해서 알려줌

#### 현대적 팩토리 패턴 변형

### 제네릭\<T> 기반의 단일 팩토리

- 생성 로직 분리
- 상속 단점 제거
- 컴포넌트 합성 + 데이터 주도 생성 담당
- 여전히 제네릭 팩토리를 역할을 수행하면서 너무 많은 팩토리 클래스 생성 방지

##### 애매해진 패턴들

### 전통적 빌더 패턴

-  복잡한 객체 생성 과정과 표현 과정 분리
  - 동일한 생성 절차에서 서로 다른 표현 결과를 만들 수 있게 함
  - 유니티 프리팹이 이미 빌더 역할을 함
  - 프리팹을 사용하되 필요한 데이터를 설정하는 것이 더 효율적

### 전통적 프로토타입 패턴

- 자기 자신을 깊은 복사해 완전히 동일 객체를 리턴하는 Clone() 강제 패턴
  - 유니티는 Instantiate가 있어서 굳이 프로토타입 패턴을 구현할 이유가 없음

### 전통적인 추상 팩토리 패턴

- 서로 연관된 인터페이스들의 묶음들을 상속받아 테마별 공장 클래스를 따로 만드는 패턴
  - 데이터 드리븐으로 해결 가능
