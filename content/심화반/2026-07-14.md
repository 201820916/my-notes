# QA란?

개발 프로세스 전반에 관여하여 버그가 발생하지 않도록 예방

프로젝트 전체의 품질 수준을 관리

단순한 버그 관리 X -> 프로젝트의 치명적인 리스크를 조기에 발견하고 통제 


## QA 예시

1. 가용성 확보 
	- 게임이 튕기지 않고(Crash), 결제가 막히지 않으며, 데이터가 유실되지 않도록 보장

2. 성능 최적화
	- 저사양 기기에서 플레이 가능한지 검토
	- 프레임 드랍이 게임 경험을 해치지 않는지 기술적 검토

3. 예외 상황 발굴
	- 인벤토리가 가득 찬 상태에서 보상을 받으면 어떻게 되는가?
	- 네트워크가 끊긴 순간 결제를 누르면? 같은 기획자가 놓치기 쉬운 빈틈을 찾아냄

4. 논리적 무결성 : 기획서 단계에서 오류를 잡아내면 개발 비용을 1/10으로 줄일 수 있음

5. 첫 인상 결정
	- 튜토리얼에서 버그를 겪은 유저는 다시 돌아오지 않음
	- 유저의 이탈 리스크를 줄이는 작업 -> 마케팅 비용의 극대화

6. 공정성 유지
	- 어뷰징이나 복사 버그 등을 사전에 차단 -> 게임 내 경제 생태계와 밸런스 보호 

# 품질의 역사와 아타리 쇼크

## 아타리 쇼크

- 당시 북미 가정용 게임 시장의 강자 아타리가 무너진 사건
- 파산을 넘어 북미 게임 산업 전체를 3년간 마비 시킴

### 원인

1. 서드파티 난립 : 아무나 게임을 만들어 팔 수 있음 -> 조악한 수준의 게임 우후죽순 생성

2. 살인적 개발 일정 : 영화 ET의 흥행에 맞추기 위해 6주만에 게임을 개발하여 QA 없이 출시

3. 유저의 신뢰 붕괴 : 돈을 주고 산 게임이 플레이 불가능한 수준 -> 게임 구매 중단


#### 기술력 부족이 아닌 QA 무시의 결과

- 우리나라도 최근 발생한 메이플 키우기와 운빨존많겜의 QA 이슈
	- "공속 프레임 이슈", "어빌리티 확률 이슈", "생명력 관련 이슈"
	- "캐릭터 가챠 확률 이슈"


# 게임 개발 프로세스와 QA의 타임라인

## 컨셉 및 기획 단계

QA의 역할 : 정적 테스트

1. 기획서 리뷰 : 기획서 내 논리적 모순, 예외 상황(Edge case) 누락을 사전에 발견
2. 테스트 전략 수립 : 이 게임의 핵심 재미 요소와 기술적 난이도를 파악하여 필요한 테스트 계획

## 구현 및 개발 단계

QA의 역할 : 형성적 테스트

1. 단위/통합 테스트 지원 : 기능 단위로 구현될 때 마다 기획 의도와 일치하는지 확인

2. 빌드 관리(Smoke Test): 매일 생성되는 빌드가 테스트 가능한 수준인지 확인하여 개발팀 피드백

3. BTC(Bulid Transfer Checklist) : 개발팀에서 QA팀으로 빌드를 넘길 때 최소한의 체크리스트를 준수 했는지 확인


## 알파 및 베타 단계

QA의 역할 : 본격적인 검출 및 리스크 평가

1. 알파(Alpha) : 모든 기능이 구현된 상태에서 기능 간 충돌과 시스템 전체의 무결성 테스트

2. 베타(Beta) : 밸런스, 호환성(다양한 디바이스), 서버 부하 등을 테스트 하며 실제 유저 환경과 유사한 상태에서 검증

3. 버그 수정 확인 : 버그를 고쳤을 때 다른 곳이 망가지지 않았는지 반복 확인


## 런칭 및 라이브 단계

 QA의 역할 : 최종 승인 및 유지보수

1. 마켓 검수(FQA) : 각 스토어(Google, Apple, Steam etc..)의 가이드라인 준수 확인

2. 라이브 모니터링 : 업데이트 시 발생 할 수 있는 결함을 체크하고 유저 제보 버그를 재현하여 개발팀 전달

# QA의 핵심 역량과 마인드셋

## 분석적 사고와 "재현 경로" 추론 능력

1. 현상 너머를 보기 : "게임이 멈췄어요"가 아니라, "A 스킬을 사용한 직후 B 아이템을 장착하면 메모리 누수로 인해 프리징이 발생함"을 찾아내는 힘

2. 인과관계 파악 : 무작위 클릭 할 때도 있지만, 시스템의 매커니즘을 이해하고 버그가 발생 할 수 밖에 없는 '조건'을 설계하는 능력

## 커뮤니케이션 : "비난"이 아닌 "협업"의 기술

 QA는 지적하는 사람이 아니다

1. 중립적 태도 : 버그 리포트에 감정과 생각 섞지 말기
	- 객관적인 팩트 위주로 전달

2. 대안 제시 : 기획자와 협업할 때 가장 환영 받는 QA는 "이거 안돼요"만 말하는 사람이 아님
	- "기획 의도가 이거라면 이런 식으로 수정하는 건 어떨까요? 라고 제안하는 사람"


## 유저 대변인으로서의 마인드셋

개발 팀 내부에서 유저의 목소리를 가장 먼저

1. 불편함에 민감하기 : 개발자는 무심코 지나가는 불편한 UI/UX에 대해 끝까지 문제 제기할 용기 필요

2. 품질 기준의 고수 : "이 정도면 되겠지" 라는 타협의 유혹에서 게임의 완성도를 지키는 마지막 방어선

## 집요함과 관찰력 

확률 1%의 버그라도 실제 발생했다면 100% 사고

1. 재현의 끈기 : 100번에 한 번 발생하는 버그라도, 그것이 유저에게는 100%의 불쾌한 경험이 될 수 있음을 인지하고 끝까지 파고드는 집요함

2. 심미적 관찰력 : 픽셀 하나가 어긋나거나, 폰트가 미세하게 다른 것 까지 잡아내는 눈


QA - 유저의 즐거움을 방해하는 모든 요소를 제거



# 바로 사용 할 수 있는 실무 예시

## 실제 사용되는 소프트웨어

- Jira, Mantis, Monday, Redmine, Spreadsheets, TestRail 등등

### Check list

1. 리소스 낭비 방지
	- 메인 메뉴도 안 열리는 빌드를 가지고 QA 인력이 붙어 상세 테스트를 하는 것은 엄청난 인건비와 시간 낭비 

2. 차단 결함(Blocker) 조기 발견 : 게임 설치가 안되거나, 진입하자마자 튕기는 등의 '진행 불가' 버그를 즉시 개발팀에 되돌려 보내기(Reject)

### test_case

대부분 구글 스프레드시트나 엑셀 등을 사용

1. 검증 기준 명확화 
	- 어떤 기능을 어떤 절차와 조건으로 확인할 지 미리 정의
	- QA 마다 다른 방식으로 테스트 하는 것을 방지

2. 재현성과 추적성 확보
	- 사전조건, 입력값, 절차, 예상 결과를 문서화 해 누구든 같은 방식으로 다시 검증 후 결과 비교

3. 품질 누락 및 회귀 방지
	- 핵심 기능을 항목별로 체계화하여 중요한 테스트 포인트가 빠지는 것을 막음
	- 수정 이후 동일 기준으로 재검증 할 수 있게 함.



### Bug Report

1. 재현 가능성 확보를 통한 수리 비용 절감
	- 개발자가 버그를 똑같이 따라 할 수 있도록 '재현 경로'를 제공
	- 버그 원인 파악에 들어가는 소통 비용과 시간을 획기적으로 줄임

2. 리스크 기반의 우선순위 관리
	- 모든 버그를 한꺼번에 고칠 수 없음
	- 심각도와 우선순위를 설정 **BUT 심각도 =/= 우선순위**
	- "반드시 고쳐야 할 것" 과 "차후 수정할 것"을 명확히 구분

- 심각도 = 게임 진행의 방해, 3단계 OR 5단계로 구분 ( 최하 낮음 중간 높음 치명적 )
- 우선순위 = 회사의 목표, 3단계 / 4단계 구분 ( 낮음 중간 높음 즉시 )

- 상태 - 발견 작업중 완료 재현불가 재발생 보류 종결 작업완료
	
	- 버그 재발견 X 순서 : 발견 - 작업중 - (작업 업로드 이후) 작업완료 - 완료
	
	- 작업 완료 후 버그가 다시 발생했다면 재발생 -> 작업중 -> 작업완료 -> 완료
	
	- 재현불가 : 개발자가 직접 재현할 수 없는 경우
		- QA는 재현 경로에 있는 모든 경우의 수를 조합하여 테스트 
		- 선행 조건을 더 발견 해야 함

	- 종결 : 비 작업적인 요소로 인한 문제 해결(버그 업그레이드 등), 기획&기능의 변경

	- 보류 : 우선순위가 낮거나 더 중요한 작업이 진행중일 때
